--------------------------------------------------------------------------------
1.1 Correcting the "Collins Aerospace spoofing" story
--------------------------------------------------------------------------------
The popular narrative — "an FAA directive said Collins Aerospace avionics had
a GPS spoofing problem" — turns out to conflate TWO separate, unrelated real
events. Getting this right matters if you ever cite it, so here is what
actually happened, with sources.

EVENT A — A real receiver software bug (NOT spoofing)
  What: Collins Aerospace SBAS-capable GPS receivers (models GPS-4000S,
  GLU-2100, GLUS-2100, GLUS-2100A — used on various business jets with Pro
  Line 4 / Pro Line 21 / Pro Line Fusion avionics) had a software defect that
  mishandled a specific SBAS integrity message ("Message Type 6", under an
  IODF=3 condition). The practical effect: the receiver could fail to warn
  the crew when GPS position integrity was actually compromised.
  This is a bug in how the receiver processes a LEGITIMATE integrity
  message — it has nothing to do with an attacker spoofing signals.
  Timeline: EASA Service Information Bulletin SIB 2024-03R1 (7 Feb 2024),
  escalated to mandatory EASA Safety Directive 2025-01 / Airworthiness
  Directive 2025-0088 (16 Apr 2025, effective 30 Apr 2025), requiring
  receiver replacement by 30 Apr 2027 or before next LPV-200 approach use.
  Source: EGNOS User Support —
  https://egnos.gsc-europa.eu/news-events/news/latest-news-potential-issue-affecting-some-satellite-based-augmentation-systems
  Note: no US FAA equivalent to this specific EASA directive was found —
  only the EASA-side documents are confirmed.

EVENT B — A real GPS spoofing event, but a different one entirely
  What: Starting late September 2023 (concentrated 23-26 Sept), aircraft
  flying Airway UM688 over northern Iraq (Erbil / Sulaimaniyah / Baghdad,
  near the Iranian border) experienced coordinated GPS spoofing that shifted
  the aircraft's reported position by roughly 60 nautical miles. Critically,
  the aircraft's Inertial Reference System (IRS) accepted the spoofed GPS fix
  as a valid update, corrupting the "trusted" inertial reference itself —
  which cascaded into FMS disagree warnings, false terrain (EGPWS) alerts,
  VOR/DME failures, and UTC clock errors. At least ~20 documented incidents
  across Boeing 777/747/737, Embraer 190/600, Gulfstream 650, Challenger
  650/605, Global Express, Falcon 8X, and Learjet 45.
  Source: Ops Group — https://ops.group/blog/gps-spoof-attacks-irs/

  The FAA's response was SAFO 24002 ("Recognizing and Mitigating GPS/GNSS
  Disruptions"), issued 25 January 2024. This is a Safety Alert For
  Operators — advisory guidance, NOT a mandatory Airworthiness Directive,
  and it proposes NO automated technical detection fix. It recommends
  monitoring equipment, reporting anomalies to ATC, and being ready to
  revert to conventional NAVAIDs / analog navigation ("go analog").
  Sources: FAA SAFO 24002 —
  https://www.faa.gov/other_visit/aviation_industry/airline_operators/airline_safety/safo/all_safos/SAFO24002.pdf
  Forbes (Marisa Garcia) —
  https://www.forbes.com/sites/marisagarcia/2024/02/03/faa-tells-pilots-to-go-analogue-as-gnss-spoofing-incidents-increase/

THE HONEST TAKEAWAY:
  The industry's actual, documented 2023-2025 response to a real,
  significant GPS spoofing wave was overwhelmingly PROCEDURAL — warn crews,
  train them to recognize it, tell them to fall back to older instruments —
  not an automated detection/fusion system of the kind this project builds.
  No evidence was found of Collins Aerospace (or another major avionics
  vendor) publishing an automated spoofing-detection algorithm in response.
  That doesn't make this project's approach wrong — it makes it a genuinely
  underserved gap. Saying "the real industry response was procedural, and I
  built the automated detection layer that response didn't include" is an
  accurate, defensible thing to say — much stronger than implying you
  replicated something Collins Aerospace already ships.

1.2 How real certified avionics actually detect/mitigate GPS spoofing
--------------------------------------------------------------------------------
- RAIM (Receiver Autonomous Integrity Monitoring): a consistency check using
  redundant satellite ranges to flag a faulty satellite signal. Conceptually
  it is a statistical residual/consistency test — similar in spirit to this
  project's NIS chi-square test, just applied to raw satellite ranges
  instead of a track's own broadcast history. RAIM was designed for
  satellite-fault detection and works against unsophisticated spoofing, but
  a sophisticated attacker who spoofs a geometrically consistent set of
  signals can evade it.

- IRS/INS cross-check: an inertial reference system provides a GPS-
  independent position/velocity estimate. In principle, large GPS-vs-IRS
  divergence should flag spoofing. In practice, the September 2023 Iraq
  incidents showed IRS often ACCEPTS the spoofed GPS as a valid update
  rather than rejecting it — corrupting the very reference meant to catch
  the spoof. This is directly analogous to this project's MLAT/radar
  limitation on identity collision: an independent check is only as good as
  its independence, and if it re-trusts the thing it's supposed to verify,
  it stops being independent.
  Source: Ops Group — https://ops.group/blog/gps-spoof-attacks-irs/
  Academic: NAVLAB — "Detecting GNSS Spoofing of ADS-B Equipped Aircraft
  Using INS" — http://www.navlab.iit.edu/uploads/5/9/7/3/59735535/detecting_gnss_spoofing_of_ads_b_equipped_aircraft_using_ins_plans_2020_kujur.pdf

- ADS-B integrity parameters (RTCA DO-260B / 14 CFR 91.227): every real
  ADS-B broadcast carries machine-readable integrity metadata this project
  does not currently use:
    NIC  (Navigation Integrity Category) — containment radius around the
         reported position
    NACp (Navigation Accuracy Category - position) — 95% position
         uncertainty
    SIL  (Source/Surveillance Integrity Level) — probability the true
         position exceeds the NIC containment radius without an alert
    SDA  (System Design Assurance) — probability of an equipment fault
         producing false/misleading position data
  Source: eCFR 14 CFR 91.227 —
  https://www.ecfr.gov/current/title-14/chapter-I/subchapter-F/part-91/subpart-C/section-91.227
  A published methodology even infers GNSS interference directly from
  NACp + almanac/HDOP data broadcast in ADS-B itself:
  https://www.cambridge.org/core/journals/aeronautical-journal/article/abs/gnss-interference-detection-methodology-utilising-adsb-nacp-indicator-and-gps-almanac-data/72FEBF7BFE1541D7BF146B14BFAA4AB8
  This is a genuine, concrete extension point for this project: OpenSky's
  API does expose some of these fields, and they were not incorporated here.

- Kalman-filter/statistical detectors in CERTIFIED production avionics:
  no evidence was found of a Kalman-filter+chi-square detector deployed as
  a spoofing detector in certified, operational avionics. The technique is
  prominent in ACADEMIC and PATENT literature (e.g. "two-step Kalman filter
  for GNSS/ADS-B cyber-attack detection", Kalman-innovation-based INS/GNSS
  spoofing detection, a US patent on "Kalman filter monitors to detect
  spoofed GNSS signals") but is not confirmed as flying in production
  systems today.
  Sources: PMC — https://www.ncbi.nlm.nih.gov/pmc/articles/PMC8347918/
  IEEE — https://ieeexplore.ieee.org/document/8654615
  USPTO patent —
  https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12360249
  Research also shows a Kalman+chi-square detector can itself be
  mathematically evaded by a sophisticated attacker who spoofs a smooth,
  self-consistent trajectory — the same limitation this project's own
  report documents for the ghost-injection attack class.

1.3 Real MLAT and primary radar — and how they differ architecturally from
    this project's simulations
--------------------------------------------------------------------------------
Real vendors confirmed to build combined MLAT + ADS-B ground surveillance
systems: Saab ("Multilateration and ADS-B Solutions") and Thales ("MAGS" —
Multilateration and ADS-B Ground Surveillance System).
Sources: https://www.saab.com/products/multilateration-and-ads-b-solutions
https://www.thalesgroup.com/en/worldwide/aerospace/mags-multilateration-and-ads-b-ground-surveillance-system

THE KEY ARCHITECTURAL DIFFERENCE:
  A real Wide-Area Multilateration (WAM) network uses multiple (typically
  4+), geographically distributed, precisely SURVEYED ground receivers with
  nanosecond-level clock synchronization, computing an aircraft's position
  from the time-difference-of-arrival of its actual RF transponder replies
  — completely independent of whatever GPS-derived position the aircraft is
  broadcasting. That independence is exactly what makes it useful against
  spoofing: it doesn't matter what the aircraft's own GPS thinks its
  position is, because MLAT never asks the aircraft what its position is —
  it measures RF arrival times at fixed, known ground points and solves for
  position directly.

  This project's simulated MLAT does model the same underlying mathematics
  (TDOA, hyperbolic multilateration, solved via least-squares) and the same
  real limitation classes (poor vertical GDOP from ground-only receivers,
  coverage gaps when receivers don't bracket the area of interest — both
  found empirically during this project's own build, see Part 2 section
  2.5). What it does NOT replicate is real RF hardware, real receiver clock
  drift, real multipath in specific terrain, or a real network's station
  count and baseline engineering. That gap is stated explicitly in this
  project's own evaluation report and is the single most important caveat
  to state plainly if presenting this work: the SIMULATION is mathematically
  faithful to how real MLAT works, but is not a real sensor network.
  Source (MLAT concept generally): ICAO MLAT concept of use —
  https://www.icao.int/sites/default/files/APAC/Documents/edocs/mlat_concept.pdf

  Primary radar's role today as a specific ADS-B-spoofing backstop in
  modernized airspace is plausible (radar doesn't depend on the aircraft's
  transponder or GPS at all) but a single strong authoritative source for
  that specific claim was not found in the time available for this
  research — treat that specific framing as reasonable inference, not a
  confirmed fact, if you repeat it.

1.4 Is a synthetic attack testbed a legitimate research approach, or a
    shortcut?
--------------------------------------------------------------------------------
Legitimate, mainstream approach — this is directly relevant to defending the
project's methodology. OpenSky Network (the same live data source this
project uses) is the dominant open, real-world ADS-B dataset used across
recent academic anomaly-detection research. Multiple published papers follow
the same pattern this project does: take real OpenSky traffic and inject
simulated/synthetic attacks on top of it (one paper names an "OpenScope"
platform used this way), covering categories like spoofed velocity, spoofed
altitude, spoofed lat/long, ghost/merge injection, and replay attacks —
functionally the same attack taxonomy built here.
Sources: OpenSky Network publications —
https://opensky-network.org/about/publications
ScienceDirect — "Anomaly detection system for ADS-B data: attack vectors and
ML models" —
https://www.sciencedirect.com/science/article/abs/pii/S2542660524003573
SoK survey of ML/DL-based ADS-B anomaly detection —
https://www.researchgate.net/publication/378453553

Isolation Forest specifically is validated in this literature for ADS-B/
location-spoofing detection (one published one-class-classifier approach
reports ~93% F1 in a related scheme), which supports this project's Phase 3
choice as literature-aligned, not arbitrary.
Source: Springer —
https://link.springer.com/chapter/10.1007/978-3-031-61489-7_4

There is no single canonical industry benchmark (no "ImageNet for ADS-B") —
OpenSky is the closest thing to a shared real-data source, but attack
taxonomies, features, and severity scales vary paper to paper, which means
this project's own attack taxonomy and severity scheme, while original, sits
in a genuinely unsettled part of the literature rather than reinventing an
established standard.

================================================================================
PART 2: THE PROJECT, LAYER BY LAYER
================================================================================
This walks through every stage of the pipeline in the order data actually
flows through it: what it does, why it exists, why it was built the way it
was rather than some alternative, and what it maps to in the real world.

--------------------------------------------------------------------------------
2.1 INGESTION — pulling in the raw data
--------------------------------------------------------------------------------
WHAT: Polls OpenSky Network's REST API every 15 seconds for a bounding box
of airspace, gets back a batch of "state vectors" (one row per aircraft
currently visible: ICAO24 address, callsign, lat/lon, altitude, velocity,
heading, vertical rate, squawk, on-ground flag), and normalizes each row
into a consistent internal schema before anything downstream touches it.

WHY THIS EXISTS: Every layer above it assumes clean, consistently-typed
data. Real API responses are messy — fields can be null, malformed, out of
range, or the API can time out or rate-limit you. Centralizing "make this
raw JSON into something trustworthy" in one place means the Kalman filter,
the ML layer, and every attack generator downstream never have to
special-case a missing field themselves.

WHY THIS DESIGN: OpenSky was chosen because it's the same real-world,
open, crowdsourced data source used across the published academic
literature on ADS-B anomaly detection (see Part 1.4) — using it means this
project's results are grounded in the same kind of data real researchers
use, not a synthetic-only sandbox. Anonymous access was the starting point;
registering for OAuth2 credentials was added because anonymous access has a
small daily quota that this project's own continuous polling exhausted
during the build (a real operational lesson, documented in the evaluation
report's Phase 8 section).

REAL-WORLD PARALLEL: This is the same role a real ADS-B ground receiver
network (or an aggregator like OpenSky, ADSB.lol, or FlightAware) plays for
any downstream air-traffic system — nobody consumes raw RF decodes directly;
everything sits on top of a normalized feed.

--------------------------------------------------------------------------------
2.2 STORAGE — TimescaleDB + PostGIS
--------------------------------------------------------------------------------
WHAT: PostgreSQL with the TimescaleDB extension (for efficient time-series
storage/querying — "hypertables" automatically partition data by time) and
PostGIS (for spatial queries on aircraft positions). Three main tables:
raw_messages (audit trail of every API response), tracks (one row per
aircraft ever seen), track_state (one row per aircraft per update — the
actual time series everything else reads from).

WHY THIS DESIGN OVER ALTERNATIVES: A plain relational table would work for
correctness but not for scale or query ergonomics — this system accumulates
hundreds of thousands of timestamped rows, and time-range queries (e.g.
"give me this aircraft's history in this window") are TimescaleDB's exact
specialty. PostGIS was chosen over storing lat/lon as plain floats because
real spatial queries (distance calculations, bounding-box filters) are
both easier to write and dramatically faster with a proper spatial index
than hand-rolled trigonometry in application code. Plain SQL + a thin
repository layer was chosen over a heavy ORM deliberately — for a project
meant to demonstrate depth, keeping the SQL visible and directly testable
was judged more valuable than the convenience an ORM buys.

REAL-WORLD PARALLEL: Real air-traffic and flight-tracking platforms
(FlightAware, ADSB.lol, OpenSky's own backend) all face the same problem —
huge volumes of timestamped, geospatial data — and use time-series /
spatial-specialized storage for the same reasons.

--------------------------------------------------------------------------------
2.3 THE KALMAN FILTER + NIS STATISTICAL TEST — the physics-based baseline
--------------------------------------------------------------------------------
WHAT: A constant-velocity Kalman filter runs independently for every
aircraft (keyed by ICAO24). At each update, it PREDICTS where the aircraft
should be based on its own recent motion, then compares that prediction to
where the aircraft actually broadcast itself. The gap between prediction
and observation is the "innovation." The Normalized Innovation Squared
(NIS) — the innovation scaled by how uncertain the prediction was — is
compared against a chi-square statistical threshold: if the observed
position is a statistical outlier given the aircraft's own recent behavior,
it's flagged.

WHY A KALMAN FILTER SPECIFICALLY: Three reasons it's a better starting
choice than jumping straight to ML:
  1. It requires ZERO attack data to build or calibrate — it's a physics
     model, not a learned one, so it works from day one against threats
     nobody has seen yet.
  2. It's interpretable — every flagged anomaly comes with an exact,
     explainable reason ("this NIS value exceeds the alpha=0.01 chi-square
     threshold for this measurement dimension"), not a black-box score.
  3. It's exact and analytically justified: the chi-square threshold isn't
     a tuned magic number, it's derived from the actual statistics of the
     filter (this is the ONE threshold in the whole system that's
     mathematically derived rather than empirically tuned — see 2.8).

WHY CATEGORY-BASED PROCESS NOISE: A widebody airliner and a light aircraft
have completely different plausible turn/climb rates. A single fixed
"how much unmodeled acceleration is normal" assumption would either be too
loose for light aircraft (missing real anomalies) or too tight for fast
aircraft (flagging normal maneuvers as attacks). Three dynamics buckets
(light / transport / high-performance) with different process-noise values
fix this, using OpenSky's own reported aircraft category where available
and a velocity/altitude/vertical-rate heuristic otherwise (real OpenSky
data has that field populated only rarely, which was discovered empirically
during the build).

REAL BUG FOUND AND FIXED HERE: the first calibration pass showed a 5%
false-positive rate on real clean traffic against a 1% target. Root cause,
found by inspecting actual flagged data rather than just re-tuning blindly:
some flagged rows were airport ground vehicles with genuinely erratic,
multipath-prone GPS fixes near buildings — a different dynamics regime
entirely from airborne flight. Excluding on-ground traffic (which is also
outside this project's stated threat model — airborne spoofing, not ground
vehicle tracking) and re-calibrating the process noise against real
airborne-only data brought the false-positive rate to ~2.7%, with the
remaining gap explained by genuine, verified real-data decode glitches
(inspected directly against raw broadcasts, not assumed).

REAL-WORLD PARALLEL: RAIM (Receiver Autonomous Integrity Monitoring, used
in real certified GPS receivers) is conceptually the same idea — a
statistical consistency check that flags when redundant information
disagrees beyond what noise alone would explain — just applied one layer
up the stack here (a track's own history) instead of to raw satellite
ranges.

--------------------------------------------------------------------------------
2.4 THE ML LAYER — Isolation Forest on Kalman-derived features
--------------------------------------------------------------------------------
WHAT: An unsupervised Isolation Forest trained ONLY on features the Kalman
filter itself produces (innovation residuals, NIS, a rolling-window trend
of both, category, flight phase) — never on raw broadcast fields directly.
It learns what "normal" looks like in that feature space from real clean
traffic and flags statistical outliers.

WHY ISOLATION FOREST SPECIFICALLY (not a neural net, not a supervised
classifier): At the time this layer was built, no labeled attack data
existed yet (attacks weren't generated until Phase 6) — so the model had to
be unsupervised. Isolation Forest is specifically well-suited to rare-
anomaly, low-dimensional, tabular data like this (versus e.g. an
autoencoder, which the original project brief explicitly scoped as only a
stretch goal if time remained). It's also literature-aligned: published
ADS-B/location-spoofing research reports Isolation-Forest-based one-class
approaches achieving strong results in comparable settings (Part 1.4).

WHY FEED IT KALMAN-DERIVED FEATURES INSTEAD OF RAW DATA: This was a
deliberate constraint, not an accident. If the ML layer could see raw
lat/lon/velocity directly, it would just be re-learning a worse version of
what the Kalman filter already does exactly, analytically. Restricting it
to the filter's OUTPUT means it can only add value by catching patterns
the filter's own single-update statistical test can't see — specifically,
persistence over a rolling window (a slow drift that never trips the
single-update NIS threshold but shows up as a sustained trend).

A REAL LIMITATION FOUND HONESTLY: because it's unsupervised and trained
only on clean data, it turned out to have the SAME blind spot as raw NIS
for slow, gradual drift attacks that stay within the range of natural
clean-traffic variability — verified directly in the benchmark rather than
assumed. This is discussed as an open, real limitation, with a concrete
proposed fix (a supervised model trained on the labeled attack data that
now exists) rather than silently patched over.

REAL-WORLD PARALLEL: This mirrors a common real security-engineering
pattern — build a physics/rules-based baseline first (interpretable,
attack-data-free), then layer statistical/ML methods on top of its outputs
to catch what the baseline structurally can't, rather than replacing it.

--------------------------------------------------------------------------------
2.5 SIMULATED MLAT — independent position verification #1
--------------------------------------------------------------------------------
WHAT: A small notional network of fixed ground "receivers." For each
aircraft update, it simulates what those receivers would have measured
(time-difference-of-arrival, with injected timing noise standing in for
real receiver clock/multipath error), solves the resulting hyperbolic
positioning equations via nonlinear least-squares for an independent
position estimate, and compares that estimate against the broadcast
position.

WHY MLAT AS A SEPARATE LAYER: Because it's structurally independent of
everything above it in a way that matters. The Kalman filter and ML layer
both only ever see the aircraft's OWN broadcast stream — if an attacker
controls that entire stream and makes it internally smooth and consistent,
those two layers have nothing to catch. MLAT (in the real world, and in
this simulation once it's given a genuine "true" position to simulate from
— see Part 1.3) doesn't ask the aircraft anything; it computes position
independently. That's exactly the property needed to catch a smooth,
self-consistent lie.

WHY HORIZONTAL-ONLY, NOT FULL 3D: An early version solved for full 3D
position and got flooded with ~400m of noise-driven error even for a
well-placed aircraft, dominated by altitude uncertainty. The real
explanation, matching real MLAT engineering: a network of ground-level
receivers has poor VERTICAL geometry (GDOP) looking up at a target miles
overhead — real terrestrial MLAT systems handle this the same way, by
fixing altitude from the aircraft's own barometric report and solving TDOA
for horizontal position only, which the receiver geometry can actually
resolve well. This project adopted the same real-world workaround after
finding the same real-world problem empirically.

A REAL BUG FOUND AND FIXED: the first receiver layout clustered every
station on one side of the polling area, leaving the western part of the
bbox outside the network's geometric coverage. One aircraft there produced
a 358km "disagreement" — not noise, pure bad geometry (extrapolating from
outside the receiver network's coverage instead of interpolating within
it). Adding receivers to properly bracket the area dropped that same
aircraft's error to under 400m. This is a real, well-known MLAT engineering
concern (network coverage/GDOP) rediscovered empirically rather than
assumed from a textbook.

WHY IT'S SIMULATED AND WHAT THAT LIMITS: no real ground receivers, real RF
hardware, or real receiver clock drift exist here — see Part 1.3 for
exactly how this differs architecturally from a real Wide-Area
Multilateration network. Real-world validation in Phase 8 concretely showed
the consequence of that gap: on live traffic, MLAT's "independent"
estimate is only as independent as the ground truth it's given — and for
real traffic (unlike the synthetic testbed) there is no separate ground
truth, so MLAT could only catch gross noise, not genuine spoofing, on real
data. That limitation is stated plainly in the evaluation report rather
than hidden.

REAL-WORLD PARALLEL: Real Wide-Area Multilateration, as deployed by
vendors like Saab and Thales for air navigation service providers — see
Part 1.3.

--------------------------------------------------------------------------------
2.6 SIMULATED PRIMARY RADAR — independent position verification #2
--------------------------------------------------------------------------------
WHAT: One simulated radar site, measuring range and azimuth (polar
coordinates, not TDOA) with independent noise on each, deliberately
different physics from MLAT. Velocity is derived by differencing two
successive simulated plots a few seconds apart — the same way real primary
radar derives velocity, since radar doesn't measure velocity directly
either.

WHY A SECOND INDEPENDENT SOURCE, NOT JUST A SECOND MLAT: Real primary
radar doesn't use transponder data at all (no identity, no cooperation
from the aircraft required) and has a fundamentally different error shape
than MLAT — angular precision from a single site means error grows with
distance from that site, rather than depending on multi-receiver network
geometry. Having two verification sources with genuinely different failure
modes is what makes a fusion approach worth building at all — if they
failed in the same way, combining them would add nothing.

REAL-WORLD PARALLEL: Real ATC primary radar, used as a non-cooperative
surveillance layer independent of whatever a transponder claims — see
Part 1.3.

--------------------------------------------------------------------------------
2.7 IDENTITY (CALLSIGN) CONSISTENCY CHECK — the sixth detector
--------------------------------------------------------------------------------
WHAT: Tracks each aircraft's first-seen ("established") callsign and flags
any later broadcast under the same ICAO24 whose callsign differs from it.

WHY THIS WAS ADDED: MLAT, radar, NIS, and ML all check POSITION or
KINEMATICS. One specific attack — two real aircraft broadcasting under the
same stolen ICAO24 identifier ("ICAO identity collision") — has a real,
unfalsified position (the intruder genuinely is where it says it is), so
every position-based check is structurally blind to it by design, not by
accident. Identity consistency checks the one thing actually being lied
about in that specific attack: who the aircraft claims to be.

A REAL BUG FOUND, AND WHY THE FIX MATTERED: building this required first
discovering that the database was silently discarding callsign after
ingestion entirely (only a "latest value" field existed, incapable of
showing a mid-track change) — fixed as a schema change. Then the first
working version compared each broadcast only to the IMMEDIATELY PRECEDING
one, and measured only 10% recall on real test data — because it only
caught the exact moment identity changed, not the whole span afterward,
once the intruder's own broadcasts became consistent with each other.
Redesigning it to compare against the track's ESTABLISHED baseline instead
of just the previous row raised recall to 31.5% at 86.8% precision, and
lifted the fused detector's F1 on this specific attack class from 61.7%
(five detectors) to 70.4% (six, with identity added) — a real, measured
improvement from adding genuinely new information, not from re-tuning an
existing threshold.

REAL-WORLD PARALLEL: No confirmed real avionics system was found using
exactly this technique, but it is the same category of idea as ADS-B
integrity fields checking source consistency (Part 1.2), and conceptually
close to any system that cross-checks a claimed identity against its own
history rather than trusting each message independently.

--------------------------------------------------------------------------------
2.8 THE ADVERSARIAL TESTBED — five attack classes
--------------------------------------------------------------------------------
WHAT: A synthetic attack injector that builds five distinct attack classes
by modifying or recombining REAL, already-ingested clean flight
trajectories (ghost injection is the one exception — it has no real
substrate by definition, since there's no real aircraft to modify):
  - Ghost aircraft injection: a fully fabricated track, no real aircraft.
  - Position spoofing/drift: a real track's broadcast position is falsified
    (suddenly or gradually) while every other field stays what the real
    aircraft actually reported.
  - ICAO identity collision: two real aircraft broadcast under one stolen
    identifier, overlapping in time.
  - Track hijacking: mid-flight, a real track's continuation is swapped for
    a different real aircraft's motion pattern.
  - Replay attack: an earlier, real, already-completed recording is
    rebroadcast as if live.

Each attack has a SEVERITY parameter in a physically meaningful unit
(meters of position offset, seconds of temporal overlap, etc.), spanning a
range chosen to straddle each detector's actual calibrated threshold —
deliberately including both "obviously above threshold" and "genuinely
subtle, near the noise floor" cases, so the benchmark shows where detection
actually breaks down instead of only showing easy wins.

WHY BUILD REAL ATTACKS ON REAL SUBSTRATE RATHER THAN FULLY SYNTHETIC DATA:
this is the same pattern used across the published ADS-B anomaly-detection
literature (Part 1.4) — real traffic's natural noise, density, and
diversity can't be cheaply hand-simulated from scratch, so attacks are
built as targeted modifications of real trajectories instead.

THE HELD-OUT EVALUATION METHODOLOGY: attack variants within each class are
split train/test, STRATIFIED BY SEVERITY (not randomly shuffled) so both
halves span the same easy-to-hard range — a random split could accidentally
give training all the easy cases and testing all the hard ones, or vice
versa. One entire attack class (track hijacking) is excluded from training
completely and only ever evaluated at test time, specifically to test
whether a system tuned on the other four classes generalizes to a novel
one it has never seen — this is the single methodological choice that most
distinguishes "did I build something that actually detects attacks" from
"did I build something that memorized my own test set."

REAL-WORLD PARALLEL: this is standard machine-learning evaluation
discipline (held-out test sets, cross-class generalization testing)
applied to a security domain — the same reason a spam filter is tested on
spam types it wasn't trained on, or a fraud model is validated on a
held-out fraud pattern.

--------------------------------------------------------------------------------
2.9 EVIDENCE FUSION — combining six detectors into one score
--------------------------------------------------------------------------------
WHAT: A logistic regression over the outputs of all six detectors (NIS,
ML score, MLAT disagreement, radar disagreement, identity mismatch),
fit ONLY on the training split, producing a single 0-100 "integrity score"
per update.

WHY LOGISTIC REGRESSION AND NOT SOMETHING FANCIER: With five input features
and a few thousand labeled training rows, a simple, interpretable model was
judged the right complexity level — a more expressive model (gradient
boosting, a neural net) risks overfitting exactly this size of dataset, and
the interpretability of a linear model's learned weights is itself a real
value for a security system where "why did this get flagged" needs to be
answerable. This is stated as an open, explicitly untested question in the
project's own limitations, not claimed as definitively optimal.

WHY FUSION MATTERS AT ALL — THE CENTRAL FINDING OF THE WHOLE PROJECT: no
single detector covers every attack class. MLAT/radar catch position-based
attacks (ghost, drift, hijack, replay) near-perfectly but are nearly blind
to identity collision. NIS/ML/identity are the reverse. This was verified
empirically, not assumed: the benchmark shows each detector's real
strengths and real blind spots side by side. Fusion is valuable
specifically BECAUSE the underlying detectors fail in different, mostly
non-overlapping ways — combining detectors that all fail the same way
would add nothing, which is also explicitly discussed (ensemble learning
cannot manufacture information that isn't present in any input; it was
deliberately not used to try to fix the identity-collision blind spot for
exactly this reason — see Part 2.7 for what actually fixed it: a genuinely
new signal, not a smarter combination of the old ones).

REAL-WORLD PARALLEL: "defense in depth" / multi-sensor fusion is a
standard concept in real air-surveillance and cybersecurity architecture —
this project's central finding (each layer's blind spots are different, so
none can be dropped) is the same argument used to justify why real ATC
systems retain primary radar as a backstop even where ADS-B/MLAT is
primary (Part 1.3).

--------------------------------------------------------------------------------
2.10 REAL-WORLD VALIDATION — a documented, currently active jamming zone
--------------------------------------------------------------------------------
WHAT: Live 10-minute data collection over the Kaliningrad/Baltic corridor —
a region with real, ongoing, independently documented GPS jamming (see
Part 1.1's Event B and the sources cited there) — compared against a
matched clean control window from the project's normal Western-Europe
traffic.

WHY LIVE COLLECTION INSTEAD OF A HISTORICAL ARCHIVE: OpenSky's true
historical database requires institutional/academic access this project
doesn't have, and the one practical free bulk archive turned out to be
multi-terabyte global daily dumps impractical to filter to one region (this
was investigated and rejected for concrete, stated reasons, not skipped).
Because the interference in this specific region is persistent and ongoing
rather than a one-off historical event, live-collected data is a genuine
sample of currently-affected real traffic — not a weaker stand-in for
history.

WHY THIS IS EXPLICITLY A "PLAUSIBILITY CHECK," NOT A LABELED EVALUATION:
real GPS jamming doesn't come with a per-aircraft, per-timestamp "this
broadcast was affected" label the way synthetic injection does — so this
section reports detection ACTIVITY RATE (what fraction of updates got
flagged), not precision/recall/F1, and says so explicitly rather than
implying a rigor the data doesn't support.

WHAT IT ACTUALLY SHOWED: NIS and ML — the two detectors that check a
track's self-consistency with no independent ground truth needed — showed
2.7x-3.8x more flagged activity in the jamming zone than the clean control.
MLAT and radar showed LOWER activity there, and rather than treat that as
a disappointing result to downplay, the report explains exactly why: for
live real traffic there is no separate ground truth the way the synthetic
testbed has, so a spoofed-but-smooth broadcast looks consistent to MLAT/
radar by construction — the same real limitation documented for real IRS/
GNSS cross-checks in the actual September 2023 Iraq incidents (Part 1.2).

REAL-WORLD PARALLEL: This is the closest thing in the whole project to
what real operators actually did in response to the 2023 spoofing wave —
observe real, documented interference and characterize what changes,
rather than only trusting a synthetic lab result.

--------------------------------------------------------------------------------
2.11 ENGINEERING SCAFFOLDING — why it matters as much as the algorithms
--------------------------------------------------------------------------------
- Externalized configuration (config.yaml): every threshold, bounding box,
  receiver network, and hyperparameter lives in one file, not hardcoded —
  this is what let every threshold be re-tuned against real data without
  touching code, and is standard practice for any system meant to run
  against changing real-world conditions.
- 125 unit tests: covering the Kalman filter's math directly (not just
  end-to-end behavior), the NIS calculation, the MLAT/radar solvers
  (including exact zero-noise recovery checks), every attack generator's
  structural correctness, and the held-out split's guarantees. This is what
  makes it possible to trust a threshold change didn't silently break
  something else.
- Structured (JSON) logging at every pipeline stage: ingestion counts,
  tracks updated, detections fired — this is what made every bug in this
  project's own build (the ground-vehicle NIS contamination, the MLAT
  coverage gap, the OpenSky quota exhaustion, the Docker build being
  silently masked by a pipe) actually discoverable, rather than a silent
  wrong number.
- Docker Compose: single-command bring-up of the database and ingestion
  service — the same operational convenience real deployed systems need.

PART 3: HOW THIS COMPARES TO OTHER PROJECTS, AND WHAT COMPANIES EXPECT
================================================================================
This section is based on a dedicated research pass (GitHub search, academic
literature search, and general ML/security hiring-signal research). Where
evidence was thin, that is stated explicitly rather than papered over.

--------------------------------------------------------------------------------
3.1 Compared to other student/hobbyist portfolio projects
--------------------------------------------------------------------------------
The most-cited comparable hobbyist project is "Fly Catcher" (GitHub:
ANG13T/fly-catcher) — a student-built system on a Raspberry Pi + SDR
hardware, using a single CNN classifier trained on real 1090MHz ADS-B
signal data plus ADS-B Exchange samples. It has a real deployed hardware
artifact and a public writeup, but: one detector (a single CNN), no visible
held-out evaluation methodology, no multi-source fusion, no adversarial
testbed with a defined attack taxonomy.
Sources: https://github.com/ANG13T/fly-catcher
https://medium.com/@angelinatsuboi/detecting-hacker-aircraft-using-artificial-intelligence-ec249baa866b

Beyond that, generic "Isolation Forest on some dataset" repos are common as
standalone ML exercises (air quality, network traffic) but none combine
with ADS-B or a second independent detector. `ADSBexchange/mlat-server` is
a real, production multilateration server — but it's community
infrastructure, not a solo portfolio/demonstration project, and it doesn't
do spoofing detection itself.

HONEST FINDING: no public student/hobbyist project was found that combines
a physics-based statistical filter, an ML layer restricted to that filter's
own outputs, two independently-modeled simulated verification sources, an
identity-consistency check, a five-class adversarial testbed with a
held-out class, a fusion model, AND real-event validation, in one system.
That should be read as "not found in this search," not "proven unique" —
GitHub search is inherently incomplete, and many portfolio repos have
generic names or no discoverability. But the typical pattern that WAS found
repeatedly — one detector, an accuracy number, no held-out attack-class
design — is real, and this project's breadth and evaluation discipline
clearly exceed that typical pattern.

--------------------------------------------------------------------------------
3.2 Compared to academic/thesis-level work
--------------------------------------------------------------------------------
This is where good, specific comparables exist:

- A University of North Florida Master's thesis, "ADS-B Security
  Mitigation through Multilateration," implements ONE detection method
  (MLAT/TDOA) rigorously, with simulated receiver networks and simulated
  adversary injection. No ML layer, no fusion, no real-event validation.
  This is a solid proxy for "what a single-detector Master's thesis in
  this specific niche looks like" — narrower in scope than this project's
  MLAT component alone, let alone the whole system.
  Source: https://digitalcommons.unf.edu/etd/1106/

- Ngamboé et al., accepted at DASC 2025 (a real IEEE avionics systems
  conference), compares Transformer vs. xLSTM intrusion detection models on
  ADS-B messages with unseen-attack testing. Peer-reviewed, single family
  of deep-learning models, no multi-sensor fusion, no simulated
  verification layer.
  Source: https://arxiv.org/abs/2510.08333

- Habler & Shabtai's LSTM encoder-decoder work is a widely-cited early
  academic baseline for ML-based ADS-B anomaly detection — again, a single
  method.
  Source: https://arxiv.org/pdf/1711.10192

- Stanford's GPS Lab (FAA-sponsored, Zixi Liu / Sherman Lo / Todd Walter)
  publishes on using ADS-B to detect/localize real GNSS interference,
  including validation against a real 2022 Denver interference event —
  genuinely close in spirit to this project's Phase 8, though their
  detection target (localizing RFI) differs from spoofing/anomaly
  classification.
  Source: https://web.stanford.edu/group/scpnt/gpslab/pubs/papers/Liu_ION_GNSS_2024_ADSB_Spoof_Detection.pdf

HONEST CALIBRATION: a typical Master's thesis or peer-reviewed paper in
this specific niche implements and evaluates ONE method rigorously. No
single academic source found combines a classical filter + ML + two
independent simulated sources + an identity check + a held-out adversarial
testbed + real-event validation into one system — this project's breadth
reads more like it stitches together the scope of three or four separate
papers' individual contributions into one pipeline. That is a genuine,
evidenced statement about breadth. It is explicitly NOT a claim about
research novelty, peer-review-grade statistical rigor, or depth-per-
component matching a dedicated thesis on any one piece — a thesis
that spends 100 pages on MLAT alone will have gone deeper on MLAT
specifically than this project did. Breadth and depth are different axes,
and this project should be presented as strong on the first, honest about
being more moderate on the second (see 3.4).

--------------------------------------------------------------------------------
3.4 Honest assessment — what's good, what's weaker
--------------------------------------------------------------------------------
WHAT'S GENUINELY GOOD, with evidence:
  - Held-out evaluation discipline (stratified train/test split, one class
    fully excluded from training) — this specific practice was flagged by
    real hiring-signal research (3.5) as something senior reviewers
    explicitly check for, and it's implemented correctly here, verified by
    the closed train/test gap after fixing a small-sample artifact
    (Part 2.8's evaluation report cross-reference).
  - Multiple real bugs found and fixed via the same "build, verify against
    real data, root-cause, fix, re-verify" loop a real engineering team
    uses — not staged, genuinely discovered during the build (documented
    with before/after numbers throughout Part 2).
  - Breadth: six independent detectors with genuinely different failure
    modes, combined via fusion, benchmarked against each other — this
    specific comparison (which method catches what, and why) is the kind
    of result that's actually informative, versus a single accuracy number.
  - Engineering discipline (125 tests, externalized config, Docker, real
    structured logging) that a from-scratch algorithm project often skips.
  - Real-world validation against a genuinely, independently documented
    interference event, with the ground-truth limitation stated plainly
    rather than glossed over.

WHAT'S GENUINELY WEAKER, stated plainly:
  - Sample sizes in the synthetic benchmark are modest (roughly 10-20
    attack variants per class) — no confidence intervals are reported, so
    a recall of "79.7%" carries real unstated sampling uncertainty.
  - Single train/test split, single random seed — no k-fold or repeated-
    trial variance check exists to show how stable these numbers are.
  - Single geographic region (Western Europe) and a short real-world
    validation window (10 minutes) — generalization across regions/time is
    untested, not just unbuilt.
  - The fusion model (logistic regression, 5 inputs) was never compared
    against an alternative (e.g. gradient boosting) — a reasonable,
    stated, deliberate choice for this data size, but genuinely unexplored.
  - Real ADS-B integrity fields (NIC/NACp/SIL/SDA — see Part 1.2) that real
    avionics already broadcast are not used anywhere in this pipeline, even
    though they're a directly relevant, available signal.
  - ICAO identity collision remains a hard ceiling for every method
    (~70% F1 at best even after adding the identity check) — a real,
    architecturally-explained limitation, not a bug, but still a ceiling.
  - No comparison against any of the academic baselines found in 3.2 (e.g.
    an LSTM-based detector) — the project benchmarks its own six methods
    against each other, but not against a published external baseline.

3.5 What companies/recruiters actually look for in a project like this
--------------------------------------------------------------------------------
No aviation-security-specific hiring source was found (e.g. no
uAvionix/Aireon engineering-blog "what we look for in candidates" post) —
this section is general ML/security hiring guidance from credible sources,
extrapolated to this project, and should be read as that, not as
domain-specific fact.

Consistent findings across multiple credible sources:
  - Reviewers weight the FULL workflow (preprocessing, evaluation,
    deployment) over algorithmic sophistication alone — a project that
    "mimics a real ML workflow end to end" is rated above one that's just
    a notebook with a good model.
    Source: https://letsdatascience.com/blog/the-ml-portfolio-that-actually-gets-you-hired-in-2026
  - Reproducibility is a hard gate: a README that explains what it does and
    how to run it, and code that actually runs, is repeatedly described as
    make-or-break — "if it fails in three commands, the review is over."
    Source: https://soltech.net/what-do-hiring-managers-actually-look-for-in-a-github-portfolio/
  - Eugene Yan (Senior Applied Scientist, ex-Amazon, now Anthropic)
    describes explicitly reviewing HOW a train/validation/test split was
    built, what offline metrics were chosen, and whether train-time
    features would really be available at inference (leakage) — this maps
    directly onto this project's held-out split and its train/test
    stability check (Part 2.8) as a real, checked signal, not decoration.
    Source: https://eugeneyan.com/writing/mechanisms-for-projects/
  - For security-flavored portfolios specifically, the consistent theme is
    "evidence over claims": can you find and explain a specific failure
    mode, document your process, communicate risk clearly — more than raw
    cleverness.
    Sources: https://www.securityscientist.net/blog/complete-guide-to-building-a-security-portfolio-that-beats-any-certification/
    https://www.cybersecuritydistrict.com/a-step-by-step-guide-to-building-a-cybersecurity-portfolio/

WHAT THIS MEANS FOR THIS SPECIFIC PROJECT: on every one of these named
criteria — held-out evaluation done correctly and explained, reproducible
end-to-end deployment (Docker Compose), a written report that states
process and limitations rather than just results, and multiple concretely
explained failure modes/bug fixes — this project already does the thing
the research says gets checked. That is a stronger match to what's actually
evaluated than raw algorithmic novelty would be, which is worth knowing:
you do not need to make the detection methods fancier to make this project
"more hirable" — the evaluation discipline and honesty already in it, per
this research, is closer to the actual signal reviewers look for than a
bigger model would be.

--------------------------------------------------------------------------------
3.6 Do companies "expect" a project like this?
--------------------------------------------------------------------------------
Direct answer: no — a project at this breadth is above the typical bar for
a portfolio piece, based on what was found in 3.1 and 3.2. Most comparable
public student work is single-detector with no held-out design; most
academic work in this specific niche is single-method with formal rigor on
that one method. This project's breadth (six methods, fusion, adversarial
testbed with held-out class, real-event validation) exceeds the typical
comparable found in both categories.

What companies DO expect, based on 3.5, is not "did you build something
this broad" but "can you demonstrate the practices in 3.5 on whatever you
built, and can you talk about it honestly." A much smaller project that
nails held-out evaluation, reproducibility, and honest limitation-reporting
would score well by the same criteria. This project happens to combine that
discipline WITH real breadth, which is a genuine differentiator — but the
discipline, not the breadth, is what the hiring research says is actually
being checked. Presenting it that way (lead with the process and the
specific bugs found, not with "I built 6 detectors") is the more accurate,
more defensible framing in an interview.
